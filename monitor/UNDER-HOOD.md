# NC-1 Nano-Monitor — Under the Hood

## 1. Назначение

Nano-Monitor — ROM-код, который предоставляет минимальный интерфейс между оператором и User RAM NC-1.

Монитор решает две основные задачи:

1. загрузка последовательности 4-битных значений из клавиатуры в RAM;
2. передача управления загруженной пользовательской программе.

Архитектура NC-1 предусматривает два банка памяти: System ROM и User RAM. При `M=1` выполняется System Bank, при `M=0` — User Bank. Инструкция `STR` независимо от текущего режима направляет запись в RAM (за исключением области MMIO `0xF0..0xFF`, которая перехватывается аппаратно). Это позволяет ROM-монитору загружать пользовательский код без переключения CPU в User Mode.

## 2. Точка входа

После аппаратного reset процессор имеет:

```text
PC = 0x00
SP = 0xF
R  = 1
M  = 1
```

и начинает выполнение с `0x00`.

`0x00` является единой точкой входа для reset и `SWI`.

Это позволяет использовать один и тот же механизм возврата из пользовательской программы:

```text
User RAM
   |
   | SWI
   v
PC = 0x00
M  = 1
   |
   v
Nano-Monitor
```

При этом флаг `R` (бит 3) используется архитектурой для различения hardware reset и software interrupt. В оптимизированной ревизии монитора проверка осуществляется маскированием: `LDI 0x8; AND B`.

## 3. System Mode и User Mode

Поле `M` регистра `FL` определяет активный банк:

```text
M = 1    System ROM
M = 0    User RAM
```

`SWI` аппаратно устанавливает:

```text
M = 1
PC = 0x00
```

`RETU` возвращает:

```text
M = 0
PC = SPC
```

`SWI` также сохраняет адрес возврата в `SPC_H/SPC_L`.

Nano-Monitor использует `SWI` не для продолжения пользовательской программы, а как механизм возврата из неё в монитор.

## 4. Почему загрузка выполняется из ROM

Обычная загрузка выглядела бы проблематично: монитор находится в ROM, а пользовательский код должен находиться в RAM.

NC-1 решает эту проблему аппаратно.

`STR` направляет запись в User RAM независимо от значения `M` (в диапазоне адресов `0x00..0xEF`). 

Если целевой адрес попадает в область `0xF0..0xFF`, работает жесткая аппаратная логика MMU: запись перенаправляется на периферию (MMIO), что позволяет монитору выводить данные на индикаторы.

Таким образом:

```text
           System ROM
               |
               | STR (0x00..0xEF)
               v
           User RAM
```

Переключать `M` для каждой записи не требуется. Это одно из ключевых свойств архитектуры NC-1.

## 5. Адресация пользовательской программы

Для пользователя выделена область:

```text
0x10 .. 0xCF
```

Это 192 nibble.

Область:

```text
0x01 .. 0x0F
```

зарезервирована как Zero Page для состояния ОС и сохранения пользовательского контекста.

Аппаратный стек расположен отдельно:

```text
0xE0 .. 0xEF
```

MMIO:

```text
0xF0 .. 0xFF
```

Поэтому Nano-Monitor не должен загружать пользовательский код в `0xD0` и выше.

## 6. Формат команды LOAD

Команда:

```text
A HH LL
```

означает:

```text
LOAD address = 0xHHLL
```

После чтения адреса монитор переходит в `LOAD_LOOP`.

Каждый следующий введённый nibble становится очередным байтом адресного потока:

```text
RAM[address] = nibble
address++
```

Поскольку память адресуется nibble-адресами, один введённый символ hex соответствует одной ячейке RAM.

## 7. Почему `F0` является терминатором

`F` — opcode `SYS`.

`F0` — инструкция `HLT`.

Других свободных SYS-кодов, которые можно было бы безопасно использовать как терминатор, спецификация не оставляет: определены `F0`, `F1`, `F4`, `F5` и `F6`.

Поэтому используется протокол:

```text
F0    end of LOAD
FF    literal F
```

Алгоритм:

```text
read nibble
   |
   +-- not F --> store
   |
   +-- F
       |
       +-- next = 0 --> END
       |
       +-- next = F --> store F
       |
       +-- otherwise --> продолжение escape protocol
```

Такой механизм позволяет различать служебный `F0` и настоящий машинный код `F0`, если последний передаётся через escape.

## 8. Считывание клавиатуры

Клавиатура использует два MMIO-регистра:

```text
0xF4  GPI_KBD
0xF5  KBD_CODE
```

В `F4`:

```text
bit 0 = 1    клавиша нажата
bit 0 = 0    клавиша отпущена
```

`F5` содержит 4-битный код нажатой клавиши.

Монитор использует polling через стандартную инструкцию `LDR`, так как область MMIO аппаратно исключена из логики переключения банков, и применение `LDRA` для опроса периферии избыточно:

```text
WAIT_PRESS:
    read F4
    test bit 0
    repeat until pressed

read F5

WAIT_RELEASE:
    read F4
    test bit 0
    repeat until released
```

Ожидание release важно для интерфейса монитора: одно физическое нажатие не должно восприниматься как последовательность одинаковых клавиш.

## 9. Проверка состояния клавиши

Для выделения `KBD` используется:

```asm
LDI 0x1
AND B
```

`AND` устанавливает `Z=1`, если результат равен нулю.

Следовательно:

```text
KBD_STAT & 1 = 0
    Z = 1
    клавиша не нажата

KBD_STAT & 1 = 1
    Z = 0
    клавиша нажата
```

Флаги `Z` и `C` обновляются ALU-инструкциями, тогда как `LDR`, `STR`, `MOV` и `LDI` их не изменяют.

## 10. Индикация

Четыре дисплейных регистра:

```text
F0  DISP_0
F1  DISP_1
F2  DISP_2
F3  DISP_3
```

в версии 4.2 имеют `R/W`.

Документация прямо допускает использование дисплейных регистров как вспомогательных storage nibbles.

Nano-Monitor использует дисплей как пользовательский интерфейс.

Концептуально:

```text
DISP_3 : DISP_2 = текущий адрес
DISP_1           = последний введённый nibble
DISP_0           = состояние/режим
```

Например:

```text
2 7 A L
```

можно интерпретировать как:

```text
address = 0x27
input   = A
mode    = LOAD
```

Точный символ режима зависит от того, какое значение монитор записывает в `DISP_0`.

## 11. Роль X и Y

Регистры `X` и `Y` содержат 8-битный косвенный адрес:

```text
X:Y
```

Например:

```asm
LDI 0x2
MOV X,A
LDI 0x7
MOV Y,A
```

создаёт адрес:

```text
X:Y = 0x27
```

Затем:

```asm
STR
```

записывает:

```text
RAM[0x27] = A
```

Именно поэтому загрузчик может последовательно изменять `Y` и при переполнении переходить к следующему `X`. 

В текущей оптимизированной ревизии монитора (203 ниббла) адресные регистры `X` и `Y` инициализируются напрямую чтением дисплейных регистров `0xF3` и `0xF2` с помощью `LDR`, минуя промежуточное сохранение в Zero Page.

## 12. Инкремент адреса

Обычный случай:

```text
0x27 -> 0x28
0x28 -> 0x29
...
0x2F -> 0x30
```

Реализуется:

```asm
INC Y
JC NEXT_PAGE
```

`INC` устанавливает `C=1`, если произошёл overflow:

```text
0xF + 1 -> 0x0
```

и устанавливает `Z=1`, если новый результат равен нулю.

## 13. Запуск программы

Команда:

```text
B HH LL
```

получает адрес пользовательской программы.

Монитор устанавливает:

```text
PCH = HH
PCL = LL
```

Но перед записью `PCL` необходимо перевести CPU в User Mode:

```asm
LDI 0x0
MOV FL,A
```

Затем:

```asm
MOV PCL,A
```

Запись в `PCL` немедленно изменяет PC и перенаправляет выполнение по адресу `PCH:PCL`.

После этого:

```text
M = 0
PC = user_address
```

и выполняется программа пользователя.

## 14. Почему не используется JMP для запуска

В отличие от `JMP`, запись в `PCL` непосредственно использует существующие регистры `PCH/PCL`.

Это позволяет подготовить адрес отдельно:

```asm
MOV PCH,A
...
MOV PCL,A
```

и использовать аппаратную семантику `PCL`.

`JMP Addr` всё равно является трёхниббльной инструкцией с непосредственным 8-битным адресом. В данном случае адрес поступает с клавиатуры, поэтому использование `PCH/PCL` естественно для динамического перехода.

## 15. Возврат из пользовательской программы

Пользовательская программа выполняет:

```asm
SYS 4
```

`SYS 4` — `SWI`.

Hardware выполняет:

```text
SPC = PC
M   = 1
PC  = 0x00
```

Поэтому управление снова оказывается в ROM.

Точка входа Nano-Monitor анализирует состояние CPU и возвращается к командному циклу.

## 16. Почему HLT не используется для возврата

`SYS 0` (`HLT`) переводит CPU в состояние halt до аппаратного reset.

Это не механизм возврата из пользовательской программы.

Поэтому:

```asm
HLT
```

означает:

```text
остановить компьютер
```

а:

```asm
SYS 4
```

означает:

```text
вернуться в System Mode
```

## 17. Hardware Stack

`CAL` и `RET` используют отдельный аппаратный стек:

```text
0xE0 .. 0xEF
```

`SP` является 4-битным регистром, а старшая половина адреса аппаратно фиксирована как `0xE`.

Таким образом:

```text
SP = 0xF
```

соответствует:

```text
0xEF
```

Стек растёт вниз.

Один `CAL` сохраняет два nibble адреса возврата:

```text
PCH
PCL
```

Поэтому 16-nibble stack поддерживает до 8 вложенных вызовов.

## 18. Взаимодействие CAL/RET с Monitor

Nano-Monitor активно использует подпрограммы:

```text
GETKEY
LOAD
RUN
...
```

Каждый:

```asm
CAL routine
```

кладёт адрес возврата в аппаратный стек.

`RET` извлекает его обратно.

Аппаратный стек обслуживается независимо от `M`, поэтому подпрограммы ROM используют тот же аппаратный механизм, что и пользовательские программы.

## 19. Cross-Bank Access и MMIO

Для ROM-кода:

```text
M = 1
```

обычная:

```asm
LDR
```

читает из ROM.

Чтобы прочитать RAM из System Mode, в архитектуре предусмотрена:

```asm
LDRA
```

то есть `SYS 6`.

Аппаратная логика выбирает противоположный банк:

```text
TargetBank = M XOR 1
```

поэтому:

```text
M=1 + LDR  -> ROM
M=1 + LDRA -> RAM
```

а для User Mode наоборот:

```text
M=0 + LDR  -> RAM
M=0 + LDRA -> ROM
```

**Важное архитектурное уточнение по MMIO:**

В ранних версиях Nano-Monitor инструкция `LDRA` ошибочно применялась для чтения периферии (клавиатуры). Однако аппаратный декодер адресов (MMU) NC-1 имеет жесткую логику: сигнал `Is_MMIO` принудительно отключает выборку из ПЗУ/ОЗУ при доступе к диапазону `0xF0..0xFF`. Запросы маршрутизируются на шину портов ввода-вывода независимо от флага `M`. 

В актуальной оптимизированной ревизии монитора инструкция `LDRA` полностью исключена. Опрос клавиатуры и чтение состояния дисплеев выполняются стандартной базовой командой `LDR`, что позволило существенно сократить размер ROM-прошивки.

## 20. Архитектура монитора

В упрощённом виде:

```text
             ROM
              |
          0x00 ENTRY
              |
              v
        +-------------+
        | Command     |
        | Loop        |
        +------+------+
               |
        +------+------+
        |             |
        v             v
      LOAD           RUN
        |             |
        v             v
      RAM          User Mode
        |             |
        |             v
        |       User Program
        |             |
        |           SWI
        |             |
        +-------------+
              |
              v
            0x00
```

Таким образом Nano-Monitor является минимальным firmware layer между пользователем и программами, размещёнными в User RAM.

## 21. Ограничения текущей архитектуры

Nano-Monitor намеренно не является полноценной ОС.

Он не предоставляет:

- редактор текста;
- дизассемблер;
- просмотр произвольной памяти;
- арифметический калькулятор;
- файловую систему;
- защиту от испорченного пользовательского кода.

Его задача — максимально простой цикл:

```text
input command
    ->
load program
    ->
run program
    ->
SWI
    ->
monitor
```

Это соответствует минимальной аппаратной архитектуре NC-1 и оставляет возможность позже расширить монитор дополнительными командами.
