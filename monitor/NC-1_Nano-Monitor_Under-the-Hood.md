# NC-1 Nano-Monitor — Under the Hood & Low-Level Architectural Hacks

Документ описывает внутреннее устройство, алгоритмы, аппаратные особенности, протоколы взаимодействия с периферией и низкоуровневые оптимизации прошивки **Nano-Monitor** для 4-битного процессора **NC-1 v4.5**.

Документ соответствует текущей рабочей версии монитора с тремя командами:

- `0` — `RUN`;
- `1` — `TAPE`;
- `2` — `DUMP`.

Отдельного режима `LOAD` нет: весь ручной ввод выполняется в режиме `DUMP` и одновременно записывается в User RAM и на накопитель.

---

## 1. Архитектурный контекст

NC-1 — 4-битный процессор с 8-битным адресом и переменной длиной инструкций. Инструкции имеют длину от 1 до 4 nibble.

Процессор использует две области памяти с одинаковым 8-битным адресным окном:

- **System ROM** — код Nano-Monitor и системные данные;
- **User RAM** — пользовательский код, данные, аппаратный стек и MMIO.

Флаг `FL.M` выбирает банк для обычной выборки инструкций:

```text
M = 1  → System ROM
M = 0  → User RAM
```

### 1.1. Особые области RAM

Некоторые области имеют аппаратную маршрутизацию, не зависящую от `M`:

```text
0xE0..0xEF  Hardware Stack
0xF0..0xFF  MMIO
```

Поэтому в System Mode Nano-Monitor может использовать `PHA`/`PLA`/`CAL`/`RET`: стек всегда физически находится в `RAM[0xE0..0xEF]`.

Аналогично, MMIO-порты `0xF0..0xF9` читаются и записываются независимо от `FL.M` обычными `LDR`/`STR`.

Это важно для монитора: `LDRA` **не требуется** для доступа к MMIO или аппаратному стеку. `LDRA` используется только для обычного чтения альтернативного банка памяти.

### 1.2. Карта адресов

```text
System ROM
0x00..0xEF  Nano-Monitor ROM
0xF0..0xFF  MMIO / не код

User RAM
0x00..0x0F  Zero Page
0x10..0xDF  User COM-area
0xE0..0xEF  Hardware Stack
0xF0..0xFF  MMIO
```

Для пользовательской программы безопасная область загрузки — `0x10..0xDF`. Область `0x00..0x0F` пользовательская программа может использовать под свои данные.

## 2. COM-модель и фиксированный адрес `0x10`

Nano-Monitor использует модель, аналогичную `.COM`-файлам DOS: стартовый адрес программы фиксирован и равен `0x10`.

Это позволяет исключить из монитора ввод и разбор адреса назначения.

При входе в `DUMP` или `TAPE` процедура `INIT_PTR` устанавливает:

```text
DISP_3 = 0x1
DISP_2 = 0x0
```

Таким образом, `DISP_3:DISP_2` одновременно являются:

1. отображаемым адресом;
2. сохранённым курсором записи в User RAM.

Отдельная переменная для курсора не требуется.

## 3. Reset-вход и размещение `CLOSE_FILE`

Начало ROM организовано специально для компактного размещения:

```asm
ORG 0x00
ENTRY:
    JMP WAIT_CMD

CLOSE_FILE:
    LDP 0xF9
    LDI 0x0
    STR
    BOOT

ORG 0x0E
RUN_XBNK:
    XBNK
```

Инструкция `JMP WAIT_CMD` занимает `4` nibble. После неё блок `CLOSE_FILE` помещается в свободное пространство перед обязательным trampoline `XBNK`.

Размер `CLOSE_FILE`:

```text
LDP 0xF9  = 4
LDI 0x0   = 2
STR       = 1
BOOT      = 2
----------------
            9 nibble
```

Поэтому при размещении:

```text
0x00..0x03  JMP WAIT_CMD
0x04..0x0C  CLOSE_FILE
0x0D        свободный nibble
0x0E..0x0F  RUN_XBNK
0x10..      основной код монитора
```

`CLOSE_FILE` используется из нескольких мест, поэтому его вынесение в общую подпрограмму экономит ROM.

## 4. Command Dispatcher — `WAIT_CMD`

Текущая версия монитора использует три команды:

```text
0 = RUN
1 = TAPE
2 = DUMP
```

Обработка построена на арифметике 4-битного кольца:

```asm
WAIT_CMD:
    CAL GETKEY
    DEC A
    JC RUN
    JZR TAPE_INIT
    DEC A
    JZ DUMP_INIT
    BOOT
```

### 4.1. Почему это работает

После `GETKEY` код клавиши находится в `A` и `B`.

Для команды `0`:

```text
A = 0
DEC A → F
C = 1
```

поэтому:

```asm
JC RUN
```

выбирает `RUN`.

Для команды `1`:

```text
1 - 1 = 0
Z = 1
```

поэтому:

```asm
JZR TAPE_INIT
```

выбирает `TAPE`.

Для команды `2` после первого `DEC` остаётся `1`; второй `DEC` даёт `0`, поэтому:

```asm
DEC A
JZ DUMP_INIT
```

выбирает `DUMP`.

Все остальные клавиши приводят к `BOOT` и возвращают монитор в начальное состояние.

Главная экономия здесь — не загружаются отдельные константы `1`, `2` и не выполняются три независимых сравнения.

---

## 5. RUN и аппаратный trampoline

Пользовательская семантика `RUN` проста: программа начинается с `RAM[0x10]`.

Фактически монитор использует trampoline:

```asm
RUN:
    JMP RUN_XBNK

ORG 0x0E
RUN_XBNK:
    XBNK
```

Последовательность:

```text
ROM: RUN
  ↓
JMP RUN_XBNK
  ↓
ROM[0x0E] = XBNK
  ↓
M: 1 → 0
  ↓
PC сохраняет траекторию и указывает на 0x10
  ↓
следующий fetch = RAM[0x10]
```

`XBNK` не изменяет `A`, `B`, `X`, `Y`, `SP`, `Z` или `C`.

Трамплин необходим потому, что смена банка должна происходить в точно контролируемой точке потока инструкций.

## 6. DUMP — ручной ввод с одновременной записью

`DUMP` начинается командой `2`.

Инициализация:

```asm
DUMP_INIT:
    MOV A,B
    LDP 0xF0
    STR
    INC A
    LDP 0xF9
    STR
```

После `GETKEY` в `B` находится `2`.

### 6.1. Индикация режима

```text
DISP_0 = 2
```

`DISP_0` одновременно является удобным MMIO-регистром состояния монитора.

### 6.2. Открытие накопителя

После `MOV A,B`:

```text
A = 2
```

`INC A` даёт `3`, поэтому запись в `STORAGE_CMD`:

```text
0x3 = MOTOR=1 + MODE=1
```

открывает накопитель для записи.

### 6.3. Ожидание READY

```asm
WAIT_DUMP_READY:
    LDR
    DEC A
    JCR WAIT_DUMP_READY
```

Контроллер возвращает `READY` в bit 0.

```text
READY = 0 → DEC 0 = F, C=1 → ждать
READY = 1 → DEC 1 = 0, C=0 → продолжить
```

После готовности выполняется `INIT_PTR`, устанавливающий адрес `0x10`.

---

## 7. DUMP — основной цикл ввода

Основной цикл:

```asm
INPUT_LOOP:
    CAL GETKEY
    INC A
    JZ ESCAPE
    MOV A,B

STORE_INPUT:
    LDP 0xF8
    STR
    CAL WRITE_RAM
    JMP INPUT_LOOP
```

Каждая обычная клавиша проходит два одинаковых пути записи:

```text
keyboard
   ├──→ STORAGE_DAT
   └──→ RAM[current_address]
```

Сначала nibble сохраняется на накопитель:

```asm
LDP 0xF8
STR
```

затем `WRITE_RAM` пишет тот же nibble в RAM.

---

## 8. Escape-автомат `F0` / `FF`

Поскольку `F` используется как первый nibble расширенных инструкций, монитор использует двухнажный escape-механизм.

После первого `F`:

```asm
INPUT_LOOP:
    CAL GETKEY
    INC A
    JZ ESCAPE
```

Для `A=F`:

```text
F + 1 = 0
Z = 1
```

поэтому выполняется `ESCAPE`.

### 8.1. `F0` — завершение

```asm
ESCAPE:
    CAL GETKEY
    DEC A
    JC CLOSE_FILE
```

Для второго nibble `0`:

```text
0 - 1 = F
C = 1
```

поэтому вызывается `CLOSE_FILE`.

### 8.2. `FF` — литеральный F

Для второго nibble `F` после `DEC`:

```text
F - 1 = E
C = 0
```

поэтому выполняется:

```asm
MOV A,B
JMP STORE_INPUT
```

В накопитель и RAM записывается `0xF`.

### 8.3. `FX`

Аналогично, `FX` для `X != 0` записывает второй nibble как обычные данные. Это позволяет вручную вводить любой поток nibble, включая машинный код, содержащий `F`.

---

## 9. TAPE — автоматическая загрузка

`TAPE` начинается командой `1`.

```asm
TAPE_INIT:
    MOV A,B
    LDP 0xF9
    STR
```

После выбора команды:

```text
A = 1
```

Запись `1` в `STORAGE_CMD` означает:

```text
MOTOR=1
MODE=0
```

то есть открыть накопитель для чтения.

### 9.1. Ожидание готовности

```asm
WAIT_TAPE_READY:
    LDR
    DEC A
    JCR WAIT_TAPE_READY
    CAL INIT_PTR
TAPE_LOOP:
    ...
```

После готовности `CAL INIT_PTR` возвращается непосредственно на первую инструкцию `TAPE_LOOP`.

### 9.2. Проверка EOF

```asm
TAPE_LOOP:
    LDP 0xF9
    LDR
    DEC A
    DEC A
    JCR TAPE_READ
    JMP CLOSE_FILE
```

В режиме чтения нормальное состояние потока:

```text
F9 = 1
```

то есть `READY=1`, `EOF=0`.

После двух `DEC`:

```text
1 → 0 → F
```

и устанавливается `C`, поэтому выполняется `TAPE_READ`.

При окончании файла:

```text
F9 = 3
```

то есть `READY=1`, `EOF=1`.

После двух `DEC`:

```text
3 → 2 → 1
```

`C=0`, поэтому выполняется `CLOSE_FILE`.

### 9.3. Чтение данных

```asm
TAPE_READ:
    DEX
    LDR
    CAL WRITE_RAM
    JMP TAPE_LOOP
```

`X:Y` после проверки статуса содержит `0xF9`. Поэтому `DEX` переводит указатель на:

```text
0xF8 = STORAGE_DAT
```

`LDR` получает следующий nibble файла.

`WRITE_RAM` записывает его по текущему адресу User RAM и увеличивает указатель.

Цикл повторяется до `EOF`.

## 10. Инициализация адреса `INIT_PTR`

Курсор записи хранится в MMIO-дисплеях:

```text
DISP_3 = high nibble
DISP_2 = low nibble
```

Инициализация:

```asm
INIT_PTR:
    LDP 0xF3
    INC A
    STR
    DEX
    DEC A
    STR
    RET
```

В вызывающих путях `A=0` после открытия режима, поэтому:

```text
INC A → 1
STR → DISP_3 = 1

DEX: F3 → F2

DEC A → 0
STR → DISP_2 = 0
```

Итог:

```text
DISP_3:DISP_2 = 0x10
```

Отдельное хранение указателя в RAM не требуется.

---

## 11. Восстановление указателя `SET_PTR`

`SET_PTR` формирует `X:Y` из отображаемого адреса:

```asm
SET_PTR:
    LDP 0xF3
    LDR
    PHA
    DEX
    LDR
    MOV Y,A
    PLA
    MOV X,A
    RET
```

Последовательность важна.

Сначала:

```text
X:Y = 0xF3
A = DISP_3
```

Старший nibble помещается на аппаратный стек.

Затем:

```text
DEX
```

даёт `X:Y = 0xF2`, откуда считывается младший nibble.

Только после этого старшее значение извлекается через `PLA` и записывается в `X`.

Итог:

```text
X = DISP_3
Y = DISP_2
```

и `X:Y` указывает текущую User RAM ячейку.

Этот порядок нельзя заменять на `MOV X,A` перед `DEX`, иначе изменится вся пара `X:Y` и адрес станет неправильным.

---

## 12. Запись в RAM — `WRITE_RAM`

Общая подпрограмма:

```asm
WRITE_RAM:
    PHA
    CAL SET_PTR
    PLA
    STR
    CAL ADVANCE
    RET
```

Она решает две задачи:

1. восстанавливает адрес `X:Y` из `DISP_3:DISP_2`;
2. записывает сохранённый nibble и продвигает курсор.

Использование `PHA/PLA` позволяет не вводить дополнительную переменную для данных.

Стек не зависит от `M`, поэтому этот механизм одинаково работает в System Mode.

---

## 13. Продвижение адреса — `ADVANCE`

```asm
ADVANCE:
    LDP 0xF2
    LDR
    INC A
    STR
    JCR ADV_HIGH
    RET
```

В обычном случае увеличивается только `DISP_2`.

Если `0xF → 0x0`, `INC A` устанавливает `C`, и выполняется `ADV_HIGH`.

### 13.1. Увеличение старшего nibble

```asm
ADV_HIGH:
    INX
    LDR
    INC A
    STR
    MOV B,A
    LDI 0xE
    SUB B
    JZ CLOSE_FILE
    RET
```

`INX` переводит указатель с `DISP_2` (`0xF2`) на `DISP_3` (`0xF3`).

После увеличения `DISP_3` получаем новый старший nibble адреса.

Если:

```text
DISP_3 = E
```

то полный адрес стал `0xE0`. Это первая ячейка аппаратного стека, поэтому дальнейшая загрузка запрещена и вызывается `CLOSE_FILE`.

Таким образом, последняя допустимая пользовательская ячейка — `0xDF`.

## 14. GETKEY — поллинг и подавление повторного ввода

`GETKEY` обеспечивает:

1. ожидание нажатия;
2. считывание hex-кода;
3. отображение кода на `DISP_1`;
4. ожидание отпускания;
5. возврат кода в `A` и `B`.

```asm
GETKEY:
    LDP 0xF4
    LDI 0x1
    MOV B,A
WAIT_P:
    LDR
    AND B
    JZR WAIT_P
    INX
    LDR
    PHA
    LDP 0xF1
    STR
    INX
    INX
    INX
WAIT_R:
    LDR
    AND B
    SUB B
    JZR WAIT_R
    PLA
    MOV B,A
    RET
```

### 14.1. Ожидание нажатия

`B=1` используется как маска `KBD`.

```asm
LDR
AND B
JZR WAIT_P
```

Пока `KBD=0`, `Z=1` и цикл продолжается.

При `KBD=1` цикл завершается.

### 14.2. Чтение кода

`INX` переводит указатель:

```text
0xF4 → 0xF5
```

после чего `LDR` читает `KBD_CODE`.

### 14.3. Dynamic Feedback

Полученный код временно записывается:

```asm
LDP 0xF1
STR
```

то есть отображается на `DISP_1`.

### 14.4. Ожидание отпускания

После возврата указателя на `0xF4` выполняется:

```asm
WAIT_R:
    LDR
    AND B
    SUB B
    JZR WAIT_R
```

Если кнопка ещё удерживается:

```text
1 AND 1 = 1
1 - 1 = 0
Z=1
```

и цикл продолжается.

После отпускания:

```text
0 AND 1 = 0
0 - 1 = F
Z=0
```

и `GETKEY` возвращает управление.

Это предотвращает многократный ввод одной физической клавиши при её удержании.

## 15. Использование MMIO как регистра состояния

В мониторе дисплеи используются не только для вывода, но и как небольшой аппаратный storage для состояния:

```text
DISP_3  → high nibble адреса
DISP_2  → low nibble адреса
DISP_1  → последний отображённый код клавиши
DISP_0  → режим DUMP (2)
```

Особенно выгодно использование `DISP_3:DISP_2`: монитор не расходует ни RAM-ячеек, ни дополнительные регистры для хранения курсора.

В режимах `RUN` и `TAPE` содержимое дисплеев функционально несущественно, поэтому в этих режимах MMIO можно использовать как временное состояние без требования поддерживать пользовательскую индикацию.

---

## 16. Escape и ROM-код `F`

Поскольку nibble `F` является префиксом `EXT`, ручной ввод машинного кода должен позволять записывать его без двусмысленности.

Используемый протокол:

```text
F0 → конец ввода
FF → литеральный F
FX → литеральный X, если X != 0
```

Это превращает ввод в простой двухсостояний автомат:

```text
NORMAL
  │
  └── F ──→ ESCAPE
             │
             ├── 0 ──→ CLOSE_FILE
             └── X ──→ STORE_INPUT
```

## 17. Оптимизации размеров кода

### 17.1. Fall-through вместо `JMP`

После ожидания `READY` в `TAPE`:

```asm
WAIT_TAPE_READY:
    LDR
    DEC A
    JCR WAIT_TAPE_READY
    CAL INIT_PTR
TAPE_LOOP:
    LDP 0xF9
```
После `RET` из `INIT_PTR` выполнение автоматически продолжается с `TAPE_LOOP`.

### 17.2. Общий `CLOSE_FILE`

Один обработчик используется для:

- `F0` в `DUMP`;
- `EOF` в `TAPE`;
- достижения границы `0xE0`.

Это избавляет от трёх копий одинакового закрытия накопителя и `BOOT`.

### 17.3. MMIO вместо переменных

`DISP_3:DISP_2` используются как persistent cursor, поэтому не требуется выделять отдельные адреса в RAM.

### 17.4. Кольцевая арифметика

`DEC`, `INC`, `JZ`, `JC` используются вместо загрузки нескольких констант и сравнения каждой команды отдельным блоком.

### 17.5. Stack как временный storage

`PHA/PLA` используются для временного сохранения nibble, когда все четыре основных рабочих регистра уже заняты полезным состоянием.

## 18. Относительные переходы

`JZR`, `JCR` и `JR` имеют длину 2 nibble и используют signed 4-bit displacement:

```text
-8 .. +7 nibble
```

Относительные переходы подходят прежде всего для локальных циклов:

```asm
WAIT_P:
    LDR
    AND B
    JZR WAIT_P
```

```asm
WAIT_R:
    LDR
    AND B
    SUB B
    JZR WAIT_R
```

```asm
WAIT_TAPE_READY:
    LDR
    DEC A
    JCR WAIT_TAPE_READY
```

Для межблочных переходов монитор использует `JMP`/`JZ`/`JC`, поскольку их дальность не ограничена диапазоном `-8..+7`.

При дальнейшей оптимизации любой `JZR/JCR/JR` необходимо пересчитывать после изменения длины кода перед ним: смещение задаётся относительно `PC_next`.

---

## 19. Граница пользовательской загрузки

Монитор загружает данные с `0x10` и прекращает запись при переходе адресного курсора на `0xE0`.

Следовательно:

```text
первый адрес = 0x10
последний допустимый = 0xDF
```

Количество доступных nibble:

```text
0xE0 - 0x10 = 0xD0 = 208 nibble
```

Область `0xE0..0xEF` не должна использоваться пользовательской программой, поскольку это аппаратный стек.

## 20. Итого: архитектура текущего Nano-Monitor

Упрощённо монитор работает так:

```text
                    ┌──────────────┐
                    │ Hardware     │
                    │ Reset        │
                    └──────┬───────┘
                           │
                           ▼
                    ROM[0x00]
                           │
                           ▼
                       WAIT_CMD
                     /     |      \
                  0 /      | 1      \ 2
                   /       |          \
                  ▼        ▼           ▼
                RUN      TAPE         DUMP
                  │        │            │
                  │        │            │
              XBNK        File       Keyboard
                  │        │            │
                  ▼        ▼            ▼
             RAM[0x10]   User RAM   RAM + Storage
                  │
                  │
                BOOT
                  │
                  └──────────► ROM[0x00]
```

Ключевые идеи реализации:

1. фиксированный COM-адрес `0x10`;
2. trampoline `XBNK` в `ROM[0x0E]`;
3. общий `CLOSE_FILE`;
4. `DISP_3:DISP_2` как persistent cursor;
5. `PHA/PLA` как временный nibble storage;
6. арифметическое распознавание команд без серии `LDI`;
7. `DEC`/`INC` + `Z/C` вместо дорогих сравнений;
8. `FF`/`F0` как компактный escape-протокол;
9. потоковый `TAPE` без промежуточного буфера файла;
10. DUMP как одновременная запись в RAM и долговременную память;
11. аппаратное ожидание `READY` и `EOF` через MMIO;
12. строгая защита границы `0xE0`, чтобы пользовательский поток никогда не записал данные поверх аппаратного стека.
